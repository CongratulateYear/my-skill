# 匹配规则与业务口径（踩坑记录）

本文件记录对账逻辑背后的业务规则和实际踩过的坑。脚本 `build_duizhang.py` 已固化这些规则；改动脚本前先读完。

## 一、匹配规则（6 级优先级）

| 级 | 规则 | 说明 |
|---|---|---|
| ① | 运营+群+厂家 全等 | 三者完全一致 |
| ② | 运营+厂家+抵扣期间 全等 | 取「抵扣在 X 货款中」的期间与钉钉结算时间比对；8.01-8.02 与 8.1-8.2 视为同期（canon 归一化） |
| ③ | 同运营+同厂家 | 唯一群直接认；多群按去噪后群名相似度取最高，≥0.55 才认 |
| ④ | 群+厂家 全等（跨运营） | 仅当该收款人在登记运营名下**没有任何付款**时才跨运营 |
| ⑤ | 收款人唯一命中 / 收款人+群名相似（跨运营 ≥0.6） | |
| ⑥ | 都不中 → 未匹配清单 | 不强行挂账 |

**核心原则：登记表的运营字段优先于群名精确；宁可同运营近似，不跨运营精确。**

### 为什么运营优先（真实事故）

曾把「群+收款人跨运营精确」排在同运营匹配之前，导致两笔挂错：
- 董奇倩 8 月 7 笔付款 6 笔属陈佳伟（cjw 宿舍床帘），仅 1 笔属陈文强（其唯一非 cwq 前缀群）；85 元后台退货被错挂到陈文强行
- 尹思军 376 元拦截被错挂到群名完全同名的张勇航 137 元小额行，实际应挂李风 4,491 元行

## 二、群名去噪

登记表与钉钉的群名写法差异极大，相似度计算前必须去噪：
- 去括号内容：「LF行李箱代发（店管家）」→「LF行李箱代发」
- 去后缀：对接群/对账群/代发群/发货群/群
- 去数字与符号：电话号码、版本号（3.9+2.2）、斜杠、空格

## 三、刷单款（破零自刷）判定

满足任一即从货款剔除：
1. 费用类型 = 破零自刷款
2. 产品=多产品 且 店铺=多店铺 且 群=多群，**且收款人属于运营人员**（不限本人；运营人员名单取付款表+登记表运营列全集，按「甲+乙/甲+丙」写法拆分）

第②类常被误填成「供应商货款」。注意例外：何法胜→李腾 43.50 元三项全多但李腾不是运营人员，不算刷单，留在货款。

## 四、扣款侧两种格式的列序差异（不能按位置取列）

- 售后台账：…|所属月份|**抵扣方式**|**金额**|备注|厂家|财务
- 汇总格式：…|所属月份|**金额**|**抵扣方式**|是否抵扣/回款|收款人

金额与抵扣方式位置互换、厂家 vs 收款人列名不同——必须按表头列名映射，禁止写死列号。

## 五、数据质量与常见陷阱

- **运营字段两边不一致**：汇总写「韩运」、钉钉写「李风」，但群+收款人一致 → 匹配不能先按运营精确过滤，靠规则④兜底
- **代发大账号**（如陈寒、刘政类）：同一支付宝账户替很多工厂收款，售后登记用真实工厂名，按收款人永远对不上 → 这些出现在「大额无售后」页属正常，建议人工按群核对
- **跨月累计抵扣**：汇款比例 >100% 的行通常是上月售后压到本月一起扣，结合匹配明细的抵扣期间核对
- **已回款记录**：现金已退回的扣款是否仍冲减货款需用户拍板；脚本默认计入但在核对总览单列
- **破零自刷款 92/93 笔群=「多群」**、收款人=运营本人，与扣款登记交集为 0，确认不参与抵扣
- **全表报销金额 vs 对账货款**：钉钉全表 SUM 含破零自刷款，与主表 G 列差值 = 刷单款；核对总览已写明勾稽关系，用户问「为什么金额不一样」时先指这一行
- **同名多版本文件 / 过期快照**（真实事故）：同一张「钉钉审批」表存在 10/8 快照与 10/20 全量两个版本，8月金额差 78 万；「拦截-罚款-退货登记」的「汇总」sheet 8月只有 222 条，而售后台账 1110 条（拦截 108 vs 634），扣款被低估 85%。所以 SKILL 规定：月份与两个文件路径必须用户本次给出并复述确认，且脚本预检会报两侧月份分布与占比。

## 六、匹配结果对数据量敏感（跨快照非单调，真实事故）

同一扣款表，付款侧用 10/8 快照匹配 216 条、用 10/20 全量反而只有 197 条。根因不是算法唯一性被破坏，而是**输入数据本身变了**：
- 陈寒（代发大账号）在 10/8 快照有 付款组「李风|LF-涵姐产品对接群|30,043」，10/20 全量表里该组消失（业务改挂为「缪文杰|寒姐&产品对接群」等）。
- 扣款记录「柴鹏远|CPY-涵姐产品对接群|陈寒」（19 条全 0 元）原本靠规则⑤跨运营群名相似挂到 LF-涵姐（去噪后 "cpy涵姐产品" vs "lf涵姐产品" ≈ 0.615 ≥ 0.6）；全量表里最相似的只剩 "寒姐&产品对接群" 0.545 < 0.6 → 未匹配。
- 结论：跨次运行的匹配单调性**无法**在单次脚本内保证（输入行会被业务改挂）。处理方式：未匹配清单给出该收款人「最接近付款组（运营｜群）」与相似度，供人工判断，**不强行挂账**。
- 0 元扣款记录只影响条数不影响金额；未匹配按「有金额 / 0 元噪声」拆开报，全 0 元的组标黄。

## 七、预检（preflight）与聚合格式

- 脚本在正式计算前逐 sheet 统计两侧目标月行数/金额/占比并打印：付款表目标月占比 <50%、扣款合计占对账货款 <3%（往期约 9%~10%）都会 ⚠；目标月 0 行直接报错并列出该 sheet 的月份分布。
- 扣款簿内多个 sheet 都含目标月数据时列出各自金额，防止选错 sheet（选中的非金额最大者 ⚠）。
- **聚合格式不支持**：如「财务登记售后」sheet（后台退货/仓库退货/罚款/拦截四列按行直接填、无逐条「类型」列、per-收款人聚合）——脚本会在两本工作簿里检测到并 ⚠；需先拆成逐条格式才能对账。

## 八、交付后必报数字

主表数据行数（另合计行 1 行）、付款总额（对账货款）、扣款总额（四类分列）、匹配条数与匹配率（金额+条数双口径）、未匹配组数与金额（有金额/0 元噪声分开）、财务空行数、大额无售后笔数。两条校验（G 列合计、四列合计）任何一条失败都不得交付。预检出现 ⚠ 时先向用户确认口径再交付。
